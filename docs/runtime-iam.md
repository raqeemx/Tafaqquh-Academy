# صلاحيات هوية تشغيل الأكاديمية

`staging-runtime-role.yaml` اسم ملف تاريخي لدور مقترح فقط؛ لم يُنشأ دور أو Staging ولم تتغير أي صلاحية سحابية. الملف يصف هوية الخادم الحالية المشتركة بين واجهات الطلبة والإدارة. لا تستخدم Owner أو Editor أو datastore.owner، ولا تمنحها إدارة المستخدمين أو قواعد البيانات أو الفهارس أو IAM أو الاستيراد/التصدير.

## أقل صلاحيات للعمليات الموجودة

| العملية | الصلاحية اللازمة |
| --- | --- |
| التحقق من تعطيل/إبطال حساب Auth وقراءة المستخدم | firebaseauth.users.get |
| بدء معاملات Firestore والتراجع عنها | datastore.databases.get |
| قراءة مستندات ونتائج الاستعلام | datastore.entities.get وdatastore.entities.list |
| إنشاء المستندات وسجل التدقيق وset عند عدم وجود مستند | datastore.entities.create |
| تعديل القرارات والتسجيلات وset لمستند موجود | datastore.entities.update |
| حذف مستند فعلي أو delete داخل معاملة | datastore.entities.delete |

أزيلت getMetadata وresourcemanager.projects.get من المقترح لأنها لا تقابل استدعاءات في هوية التشغيل الحالية، التي يحدد لها projectId صراحة. ليست هذه هوية إعداد المشروع أو بنائه؛ أدوار المنصة الخاصة بالبناء والتشغيل وتعيين أول مسؤول تُراجع منفصلة. لا تعالج خطأ IAM بمنح دور واسع احتياطيًا.

تحتاج صلاحية الحذف إلى ثلاثة مسارات مراجعة في `runtime-delete-operations.json`: تنظيف السجلات المنتهية، حذف علامة تقدم الطالب الخاصة به، وإلغاء إذن التشغيل الخاص بالـcookie. القراءة والتشغيل والنشر/الإخفاء والقبول/التعليق لا تحتاج delete بذاتها. انتهاء الإذن بمرور خمس دقائق لا يحتاج حذفًا، لكنه لا يغني عن إلغائه المبكر عند الخروج. لا تمنح صلاحية datastore.databases.delete أو حذف مستخدمي Auth.

## حدود IAM

Admin SDK يتجاوز Security Rules. الدور المشترك يمنح صلاحية حذف مستندات على نطاق قاعدة البيانات الذي ينطبق عليه، وليس على مجموعة أو مسار فقط؛ قيود الطالب والمسؤول والتحقق من cookie هي قيود تطبيقية وليست حدود IAM للمجموعات. إذا لزم لاحقًا عزل الحذف أمنيًا عن بقية الخادم، يجب فصل خدمة/هوية الصيانة وحدود البيانات، لا الادعاء أن نفس هوية التشغيل مع قواعد العميل تحقق العزل. لم ننشئ خدمة إضافية لهذه المهمة.

عند اعتماد صلاحيات فعلية لاحقًا، استخدم هوية تشغيل مخصصة واربط الدور بأضيق نطاق قاعدة بيانات مدعوم، أو تقييد المورد بشرط IAM موثق عند ملاءمته. افصل قراءة Auth على المشروع عن بيانات Firestore إن اقتضى نطاق الربط ذلك. لا تصغ شرطًا على اسم مجموعة وتتوقع منه حماية المستندات. راجع أيضًا الأدوار الموروثة؛ دور محدود إضافي لا يلغي صلاحية Owner/Editor سابقة.

## التحقق الآلي والتحقق الحقيقي لاحقًا

`npm run test:config` يفحص AST لاستدعاءات الخادم المعروفة، ويقارن صلاحيات الدور بها، ويُلزم إدراج كل موقع delete في قائمة المراجعة. يفشل عند إضافة حذف جديد أو حذف الصلاحية أو إضافة أذونات غير مستخدمة أو بعض استدعاءات الإدارة الواسعة. هذا فحص تقريبي محافظ؛ ليس تتبع أنواع كاملًا، وقد يحتاج تحديثًا عند استخراج helper أو استخدام REST أو تغيير SDK. راجع الكود والهوية ولا تعتمد عليه وحده.

المحاكيات تختبر منطق الوصول والحذف، **ولا تختبر Google Cloud IAM**. بعد إذن مستقل، على مورد اختبار موجود ومصرح به وبيانات مصطنعة فقط، يتحقق المشغّل من الهوية الفعلية والأدوار الموروثة بواسطة Policy Troubleshooter واختبارات API بتلك الهوية (لا اعتماد مالك الجهاز). تُختبر القراءة والاستعلام والإنشاء والتعديل والمعاملة والحذف الفعلي، ثم تُختبر إزالة delete من هوية اختبار مضبوطة: يفشل التنظيف ومسح علامة التقدم وإلغاء إذن التشغيل، بينما تبقى القراءة المسموحة عاملة. في فشل الإلغاء يجب أن يبقى cookie وتظهر رسالة فشل، لا نجاح وهمي.

يشمل الفحص السلبي أيضًا منع حذف مستخدم Auth أو قاعدة بيانات أو تعديل IAM، والتحقق من منع قواعد بيانات خارج النطاق. راجع سجلات التدقيق والطلبات الفعلية لتحديد أي إذن إضافي يحتاجه SDK قبل تعديل المقترح. لا يُنفذ هذا الدليل أي إجراء؛ لم تُنشأ بيئة أو هوية ولم تُكتب بيانات سحابية هنا.

المصدر: [صلاحيات Firestore وعمليات API](https://firebase.google.com/docs/firestore/security/iam).
