# تجهيز Staging مستقل — لم يُنشر

هذا الإعداد مرتبط بتحديث لوحة الإدارة ورحلة الطالب. ادمج طلب مراجعة الإدارة أولًا ثم هذا الطلب، أو اختبر الفرعين مجتمعين قبل أي نشر. لا تنشر هذا الفرع منفردًا: يعتمد فحص Staging على مسار الإدارة وشريط البيئة ونموذج الصلاحيات الجديد.

## المشروع والعزل

اقترح مشروعًا مستقلًا باسم مثل `tafaqquh-academy-staging` إذا كان المعرف متاحًا؛ لم يُنشأ. لا تستخدم `tafaqquh-academy` أو بياناته أو تطبيق الويب المسجل فيه. إنشاء موارد App Hosting وربط الفوترة قد يترتب عليه تكلفة ويتطلب موافقة صريحة قبل التنفيذ. حدود minInstances=0 وmaxInstances=2 تقلل السعة ولا تضمن انعدام التكلفة؛ فعّل تنبيهات الميزانية والمراقبة قبل التجربة.

بعد الموافقة، ينشئ مالك المشروع بيئة Firebase منفصلة وتطبيق Web جديدًا وAuth Email/Password وFirestore `(default)` في الموقع المعتمد. لا تنسخ حسابات الإنتاج أو المستندات أو الملفات. سجّل حسابات وهمية مخصصة فقط، واختر بريد اختبار تملكه لتجربة تسليم رسالة التحقق الفعلية.

## GitHub وApp Hosting من Console

1. راجع وادمج الطلبين دون تشغيل نشر إنتاجي. في مشروع Staging افتح App Hosting واربط GitHub، مع منح الوصول إلى هذا المستودع فقط. اختر جذر التطبيق `/` وNode.js 24.12+، وفرع المراجعة المعتمد/`main` بعد دمج الطلبين.
2. قبل بدء rollout، اختر اسم البيئة `staging` لتطبيق `apphosting.staging.yaml`. عطّل النشر التلقائي من الفرع أثناء الإعداد؛ استخدم rollout يدويًا بعد المراجعة. لا تغيّر إعدادات مشروع الإنتاج.
3. في Environment settings املأ القيم الفارغة في `.env.staging.example` و`apphosting.staging.yaml` من تطبيق Web الجديد. قيم Console تتقدم على YAML. اجعل معرّفات المشروع الأربعة متطابقة، وAPP_ENV وNEXT_PUBLIC_APP_ENV يساويان staging. اضبط APP_ORIGIN على أصل رابط backend التجريبي الذي توفره Console، HTTPS دون مسار أو شرطة ختامية. لا تخترع رابطًا.
4. وفّر جميع NEXT_PUBLIC_* في BUILD (وفي RUNTIME كما في القالب). Firebase Admin flag في RUNTIME؛ لا حاجة لمفاتيح JSON. لا تضف متغيرات المحاكيات أو GOOGLE_APPLICATION_CREDENTIALS. مفاتيح Web عامة بطبيعتها ولا تمنح صلاحية Admin.
5. يبقى AUTH_ENABLED وADMIN_ENABLED وPRIVACY_POLICY_APPROVED على false افتراضيًا. راجع قواعد وفهارس الطلب الأول وطبّقها على Staging فقط وانتظر جاهزية الفهارس. راجع سياسة الخصوصية واملأ controller/contact/retention. ثم فعّل الأعلام الثلاثة في Console وأعد البناء قبل اختبار التسجيل.
6. أضف نطاق backend إلى Authorized domains في Authentication. راجع قوالب البريد وكلمة المرور. عيّن مسؤول اختبار موثق بواسطة إجراء IAM الموثوق في `docs/admin.md`، ولا تعتمد على تطابق البريد فقط.
7. راجع هوية الخدمة أدناه، ثم نفّذ rollout يدويًا بعد الموافقة الصريحة. يظهر الرابط الحقيقي في لوحة backend بعد النجاح. تحقق من شريط «بيئة تجريبية» ومن المشروع المستخدم قبل إدخال أي حساب اختباري.

لا تتجاوز فشل `check-staging.mjs`: يمنع بيانات الإنتاج أو اختلاف المشروع وأعلام المحاكيات وملفات مفاتيح الخدمة. يقوم وقت البناء بقراءة إعداد Auth العامة للتأكد من تطابق API key مع رقم مشروع Staging ونطاقه؛ لا يكتب بيانات ولا ينشئ موارد. إذا فشل بسبب إعداد Auth أو قيود API key أصلح الإعداد؛ لا تعطّل الحماية. هذا فحص إعداد وليس اختبار اتصال إداري أو ضمانًا شاملًا للعزل.

## هوية الخدمة وIAM

استخدم حساب التشغيل المُدار `firebase-app-hosting-compute@STAGING_PROJECT_ID.iam.gserviceaccount.com` (تحقق من الهوية الفعلية في backend) عبر ADC. لا تمنحه أدوارًا في الإنتاج. لا تعدّل حسابات Cloud Build أو service agents لتصبح حساب التشغيل. احتفظ بالأذونات التي تديرها المنصة ولا تمنح أدوار service-agent لهوية عادية.

`docs/staging-runtime-role.yaml` قالب تاريخي لدور التشغيل، أصبح يتضمن حذف مستندات Firestore للتنظيف ومسح التقدم وإلغاء إذن التشغيل، دون إدارة مستخدمي Auth أو IAM. راجع [صلاحيات التشغيل](runtime-iam.md) وحدود النطاق واختبارات الهوية الفعلية لاحقًا بعد الإذن. لا تمنح Owner أو Editor أو Firebase Admin. أدوار المنصة منفصلة؛ هذا الملف لا يجيز إنشاء Staging أو تعديل أذونات سحابية.

Admin SDK يتجاوز القواعد ويستطيع ضمن هذا الدور تحديث مستندات Firestore؛ تحقق الخادم من المسؤول هو حاجز التطبيق، وليس عزل IAM لكل collection. اعزل مشروع Staging، وراقب Cloud Audit Logs، وافصل صلاحيات الشخص الذي يعيّن أول مسؤول عن هوية تشغيل التطبيق. لا توجد مفاتيح خدمة في GitHub أو Secrets المطلوبة لهذه البنية.

## Next.js 16.4.3

احتُفظ بالإصدار دون تغيير الاعتماديات. [توثيق Firebase للأطر](https://firebase.google.com/docs/app-hosting/frameworks-tooling) يذكر Next.js ابتداءً من 13.5 وNode.js 24.12+ فأعلى، لكن جدول الدعم النشط المعروض لا يشمل 16.4.3؛ الإصدارات الأحدث تُعامل كمعاينة. نجاح next build محليًا لا يثبت نجاح المحول أو rollout على App Hosting. لا تعتمد هذه النسخة للإنتاج قبل بناء Staging وفحص سجلات المحول والمسارات الديناميكية. إذا ظهر عائق توافق، وثّق الخطأ واقترح تعديل إصدار منفصلًا مع اختبارات؛ لا تخفض الإصدار تلقائيًا.

لا يغيّر YAML أمر تشغيل المحول ولا يضع scripts override؛ أمر package build يضيف فحص العزل ثم next build. راجع [إعداد App Hosting](https://firebase.google.com/docs/app-hosting/configure) و[هوية التشغيل](https://firebase.google.com/docs/app-hosting/about-app-hosting).

## اختبارات بعد الموافقة

محليًا: `npm run test:config` (17 فحصًا دون اتصال) مع lint وtypecheck وbuild والمتصفح والمحاكيات. لم يُشغّل smoke ضد سحابة حتى الآن.

بعد نجاح النشر المعتمد، اضبط STAGING_APPROVED=true وSTAGING_URL على الرابط HTTPS الحقيقي ثم `npm run test:staging`. هذا الاختبار المحدود يقرأ الصفحات ويرفض API المجهول فقط، ولا ينشئ حسابًا أو يكتب بيانات. الموافقة الصريحة من مالك المشروع مطلوبة قبل تشغيله؛ المتغير ليس بديلًا عن تلك الموافقة.

بعد ذلك نفّذ ببيانات اختبار مخصصة دورة القبول: إنشاء حساب وموافقة خصوصية → pending → فتح رسالة التحقق الفعلية → منع المحتوى → دخول مسؤول الاختبار → قبول ومنح برنامج تجريبي معتمد → قراءة المادة المصرح بها فقط → تعليق → منع الوصول → فحص Audit Logs ومحاولة UID آخر. راجع IAM والفهارس والبريد والـHTTPS ورفض الأصل المختلف. احذف بيانات الاختبار بإجراء IAM موثوق وفق سياسة الاحتفاظ. لا تعتبر اختبارات المحاكيات وحدها تصريحًا بالإطلاق العام.

سبب اختيار Node.js 24.12+ هو engines لحزم Firebase المقفلة حاليًا. التوثيق الرسمي يدعم Node.js 22 فأعلى ويذكر runtime nodejs24؛ اختر nodejs24 في backend بما يطابق package.json. لا تبنِ الحزم الحالية على Node.js 22 رغم نجاح بعض الاختبارات عليه.

تشغيل الاختبارات محليًا على Node.js 24.22.1؛ اعتماد App Hosting الحقيقي يبقى معلقًا حتى الموافقة والنشر التجريبي.
